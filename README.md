# webhook-buffer

웹훅을 받아서 목적지로 그대로 넘겨주는 작은 버퍼 서버입니다.
목적지가 잠깐 죽어 있거나 에러를 내도 웹훅을 잃어버리지 않도록, 전달에 실패한 웹훅은 저장해 뒀다가 성공할 때까지 다시 보냅니다.

## 동작 방식

1. 웹훅이 들어오면 메서드, 경로, 쿼리, 헤더, 본문을 그대로 목적지(`TARGET_URL` + 경로)로 보냅니다.
2. 목적지가 2xx로 응답하면 그 응답을 보낸 쪽에 그대로 돌려주고 끝냅니다. 따로 저장하지 않습니다.
3. 연결 실패, 타임아웃, 2xx가 아닌 응답이면 웹훅을 SQLite에 저장하고 보낸 쪽에는 `202 Accepted`를 돌려줍니다.
4. 백그라운드 작업이 저장된 웹훅을 성공할 때까지 계속 다시 보냅니다. 재시도 간격은 `MIN_BACKOFF_MS`에서 시작해 실패할 때마다 두 배씩 늘어나고 `MAX_BACKOFF_SECS`에서 멈춥니다. 성공하면 저장소에서 지웁니다.

저장소가 디스크(SQLite)에 있어서 버퍼 서버를 재시작해도 아직 못 보낸 웹훅은 남아 있습니다.

## 실행

```sh
TARGET_URL=https://example.com cargo run --release
```

`POST http://localhost:8080/github/events?x=1`로 들어온 요청은 `POST https://example.com/github/events?x=1`로 전달됩니다.

## 설정 (환경 변수)

| 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `TARGET_URL` | (필수) | 웹훅을 전달할 목적지 |
| `LISTEN_ADDR` | `0.0.0.0:8080` | 수신 주소 |
| `DB_PATH` | `webhook-buffer.db` | 실패한 웹훅을 저장할 SQLite 파일 |
| `REQUEST_TIMEOUT_SECS` | `10` | 목적지 요청 타임아웃 |
| `MIN_BACKOFF_MS` | `1000` | 첫 재시도까지 대기 시간 |
| `MAX_BACKOFF_SECS` | `300` | 재시도 간격 최댓값 |
| `MAX_BODY_BYTES` | `10485760` | 받을 수 있는 최대 본문 크기 |
| `RUST_LOG` | `info` | 로그 레벨 |

## 상태 확인

```sh
curl localhost:8080/_buffer/status
# {"pending":3}
```

`/_buffer/status` 경로는 버퍼가 직접 처리하고 목적지로 넘기지 않습니다.

## 알아둘 점

- 2xx가 아니면 모두 실패로 봅니다. 그래서 목적지가 특정 웹훅에 계속 400을 돌려주면 그 웹훅은 영원히 재시도됩니다.
- 이미 실패한 웹훅이 쌓여 있어도 새로 들어온 웹훅은 바로 전달을 시도합니다. 그래서 목적지에 도착하는 순서가 원래 순서와 다를 수 있습니다.
- 리다이렉트(3xx)는 따라가지 않고 실패로 처리합니다.
